## How to read this table

Every scenario asserts on up to three layers, named in the Given / when / then cell:
**Phone** is the PhoneDriver transcript (messages, edits with their `edited` flag and text history on the fake, button labels, `topicId`, toasts).
**Browser** is Playwright on the Agents page (Live Telegram panel) or Tasks page.
**Durable** is the REST API (`TelegramLiveStatus`, prompt APIs) plus read-only database inspection of `telegram_outbox`, receipts, human responses and actors, plus the Bot API calls the harness server made (`telegramCalls()`).

Tier and backend values: `T0` is a unit, migration or stubbed-HTTP test with no app boot (fetch stubbed at the HTTP layer, or the fake Telegram server on loopback for contract parity); `T1 fake` boots the harness server and web app with the fake Telegram server and the scripted fake agent; `T3 real` runs on the dedicated test bot through the route proxy and the operator's user client; `T1 fake + T3 real` means the same scenario body runs on both backends.
T4 is the operator's phone look check at L3 close-out.

Terms used in the rows:
**Edit trigger** is whatever causes the app to queue an edit of an earlier message; F1 itself ships no product caller (see findings), so until one exists it is the harness seam the operator chooses in question 1.
**Send row** and **edit row** are outbox rows with operation `send` and `edit`; "delivered" means the row reached its terminal success state, whatever the implementation names it.
**Superseded** means an edit row replaced by a later edit to the same message before it was delivered.
**Card** is a personal question card or answer card as in l1.md.
Unless a row says otherwise, the common setup is the l1.md setup: harness root with task control, Notifications and Remote actions on, Transport Telegram, one paired operator private chat (actor `topic_id` null), a fixture saved task on the fake provider, and a `block-on-decision` scenario.
Waits are on observable conditions only; "no further call" is asserted after at least two full delivery cycles have been observed (a later outbox row delivered, or a status change), never after a sleep.
Every run ends with the token sweep and the real-database-unchanged check.

## Findings from the specification and public interfaces that shape the scenarios

- F1 adds an edit operation but no product path that issues edits: the first callers are slice B navigation (`nv_` callbacks edit their message) and the queued status-message follow-up.
  T0 rows can drive the outbox directly, but T1 and T3 rows need an edit trigger reachable from outside the process, or they wait for slice B (question 1).
- `telegram_outbox.state` is constrained to `QUEUED`, `SENT` and `FAILED`, and `TelegramLiveStatus` counts `FAILED` rows with no `next_attempt_at` as `failed`.
  The specification does not say how a superseded edit or an edit to a deleted message appears in those counts; S-L3-F1-07 and S-L3-F1-12 assert that a superseded edit is never counted as queued, retrying or failed, and record how the deleted-target case appears for question 2.
- Replies are mapped to cards by looking up the newest `SENT` outbox row with a matching `sent_message_id` (`telegramOutboxBySentMessage`).
  If an edit row carries its target's message id in that column, a reply to an edited card could resolve to the edit row and be answered "That message is not a task question".
  S-L3-F1-06 guards this regardless of how the target is stored.
- On both the fake and real Telegram, `editMessageText` without `reply_markup` removes the inline keyboard.
  An edit that does not restate a card's buttons silently strips them, so S-L3-F1-06 asserts buttons explicitly after each edit.
- The fake's "message is not modified" check compares text and reply markup only, not message entities.
  Slice A adds entities (expandable blockquote); if real Telegram treats an entity-only change as a modification, the fake answers wrongly. S-L3-F1-03 makes the recorded fixtures decide.
- Neither `PhoneDriver` nor `FakeTelegramServer` can delete a message today (the fake only has `userDeletesTopic`), and `PhoneDriver.send` cannot send into a topic.
  S-L3-F1-12 and the F2 rows need both: a phone-side delete (GramJS `deleteMessages` on T3) and a topic option on send, identical on both backends.
- The recording step `editMessageText.missingMessage` edits `message_id: 1`, which in the operator's private chat may be an existing message the bot did not send, so real Telegram may answer "message can't be edited" rather than "message to edit not found".
  The fixture needed for the deleted-target case is an edit of a bot message the user client has just deleted; S-L3-F1-03 asks for that step, and S-L3-F1-13 requires both descriptions to be treated as permanent.
- Today any 4xx other than 401, 404, 409 and 429 is classified `rejected` and not retried, so without F1 a "message is not modified" response would be recorded as a permanent failure.
  S-L3-F1-02 and S-L3-F1-10 pin the success outcome at the HTTP client layer and at the outbox layer.
- Rate limiting pauses all sending, not one row, and transient failures stop the current delivery cycle.
  The rows assert only the observable contract (nothing before `retry_after`, each row delivered once, latest edit wins), not the loop structure.
- F2 before C2: `taskControlActorFor` matches `topic_id` exactly and pairing refuses a message sent in a topic, so the paired private-chat actor (topic null) is not recognised in any topic until C2 changes actor scope.
  Before C2 the only live replies that can originate in a topic are the pairing responses ("Pair from a private chat with this bot, not a group.", "This pairing code was already used."), plus every reply path for an actor whose stored topic is not null, which pairing cannot create.
  S-L3-F2-07 asserts F2 does not widen authorization; S-L3-F2-04 to S-L3-F2-06 need a topic-bound Telegram actor (question 3).
- `normalizeTelegramUpdate` reads `message_thread_id` only when `is_topic_message` is true.
  Telegram also sets `message_thread_id` on replies in non-forum chats (reply threads), where sending with that thread id fails; S-L3-F2-08 keeps that case at topic null.
- Whether private bot chats support topics, and which update fields they carry, is unverified until slice C0; the fake's `createForumTopic` accepts only chats flagged `isForum`.
  F2 topic rows therefore run on T1 in a fake forum supergroup, and the T3 topic row is blocked on C0 (or on the private-group fallback) rather than skipped.
- Protocol 7a says a reply that answers a card must arrive in that card's thread, otherwise it is rejected like a reply to a non-question; the engineering plan places that rule under C2.
  S-L3-F2-06 asserts only the durable safety outcome and the reply's topic, and accepts either silence or a rejection text (question 4).
- The specification says replies to a thread that no longer accepts messages must not be redirected only for `create_thread` rows; it is silent for a reply whose incoming topic was closed or deleted between receipt and send.
  S-L3-F2-09 asserts no redirection and no endless retry, and records the outcome for question 5.
- Real Telegram cannot be made to return 429 or 5xx on demand, so those variants are T1 only; the T3 outage row uses `network.cutTelegram()`.

Questions for the operator:

1. Edit trigger for T1 and T3 in F1: accept a harness-only seam (active only under `AGENT_CONSOLE_HARNESS=1`, loopback only, covered by the guard tests) that queues a send and edits of it through the same outbox the product uses, or move the F1 T1 and T3 rows into slice B, keeping F1 at T0 only?
   Recommendation: the seam, so F1 closes on its own evidence and B's navigation rows can rely on a proven edit path.
2. Should an edit whose target message was deleted count in the Live Telegram panel's `failed` outbox count and set `lastError`?
   The operator deleting a message is normal use, so a permanent "failed" badge may read as a fault; the specification only says "recorded as failed without retry".
3. F2 topic paths for an authorized actor: may a T1 fixture create a topic-bound Telegram actor directly in the temporary root's database (the harness durable layer is otherwise read-only), or are those paths covered at T0 until C2 makes private-chat topics authorized?
4. In F2 (before C2), should a reply in topic Y to a card sent in topic X produce a rejection message in Y, or stay silent until C2?
5. When the incoming message's topic is closed or deleted before the reply is sent, should the reply be dropped as failed (current recommendation), held until C2's thread registry can recreate or reopen the topic, or sent to General?
6. After a chat is unpaired, should edits already queued for that chat's messages still be delivered?
   S-L1-24 requires no outbox row addressed to an unpaired chat; S-L3-F1-20 assumes queued edits are also dropped, and at minimum never deliver working buttons.
