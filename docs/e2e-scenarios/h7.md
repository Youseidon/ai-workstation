## How to read this table

Covers uses harness plan section references, as in [h0-h4.md](h0-h4.md): `3-P2` is accuracy principle 2, `4.4-func` the functional checks of section 4.4, `4.4-console`, `4.4-overflow`, `4.4-overlap`, `4.4-axe` and `4.4-shot` its four UI quality checks, `4.4-review` its agent-first diff review, `5-T2` the T2 tier row, `7-baseline` the baseline approval row of section 7, `11-noisy` the noisy screenshot risk, `H7` the slice text in section 9, `H7-po` its page objects, `H7-retire` the script retirement and `H7-done` its definition of done.
`VHI-nn`, `VM4-nn` and `VP6-nn` are the checks of the three retired scripts, enumerated in the coverage check section at the end.
Tier T0 means a harness self-test on fixture pages (the selftest Playwright config) or a unit test, with no app boot.
Tier T1 means a functional scenario on a booted harness (temporary root, fake Telegram where needed, fake provider).
Tier T2 means the UI quality project (`npm run e2e:visual`) on a booted harness with a fixed fixture dataset.
All rows use the fake Telegram backend or none; no H7 row needs real Telegram.

**The quality check set (QC)** is applied by every T2 row, and by every T1 row at each view it visits, at 1440x1000 and at 390x844 unless the row says otherwise:

1. No console errors, no uncaught page errors and no failed requests (`pageHealth`), except entries on that row's own explicit allowlist, each with a reason.
2. No horizontal document overflow (`scrollWidth` greater than the viewport width), except inside an element that is itself a horizontal scroll container by design.
3. No overlapping interactive elements (buttons, links, inputs, selects, elements with an interactive role), computed from bounding boxes of visible, non-inert elements, and no interactive element cut off at the viewport's left or right edge.
4. axe-core with zero serious or critical violations, other than entries on the explicit exception list of S-H7-04.
5. Every `button` has `type="button"` or sits inside a form (S-H7-09).
6. Screenshot comparison against the approved baseline for that screen, state and width, with the dynamic regions of that screen masked (S-H7-05 to S-H7-08).
7. The DOM text at capture time goes to the token sweep.

**States** means, per view: empty (fresh fixture with nothing to show), loading (the view's API responses held by the test until it releases them, so the loading state is captured without a sleep; the responses are the real server's, only delayed), populated, and error (`stopServer()` so the view's load fails, with the resulting failed requests and console errors on that row's allowlist only).

## Findings from the plan and existing interfaces that shape the scenarios

These are facts the implementing agent must respect, or flag if the plan disagrees.

- `/sessions` redirects to `/activity`; the "Sessions" page object of plan section 9 is the Activity view's session list and detail.
  `/fleet` redirects to `/agents`, `/operations` to `/tasks` keeping its query, and `/input?prompt=N` to `/tasks?filter=attention&prompt=N`.
  `verify-phase6.mjs` still visits `/operations` and `/fleet`, so its "rendered app chrome" checks have been exercising redirects, not views (S-H7-14).
- `verify-human-input.cjs` intercepted every write and fulfilled `clarify` and `respond-and-continue` with invented responses, and `verify-m4-browser.mjs` rendered two components with hand-written CSS instead of the app's stylesheet.
  Neither ever proved the real server path or the real layout, so H7 rows replace them with the real app, the real server and the fake provider rather than porting the mocks.
- Plan 4.3 lists the fake provider behaviours `block-on-decision`, `done`, `fail`, `hang-until-stopped`, `crash-after-spawn` and `consume-answer`.
  Two H7 flows need behaviour that list lacks: answering a clarification run with text (S-H7-37), and holding a step open until the test releases it, then reporting DONE, so Pause can be pressed deterministically while a station runs (S-H7-43).
  Adding them is inside H7's scope but is harness work beyond page objects.
- START_UNKNOWN arises when the server loses a run without knowing whether the provider stopped (H-M2-03).
  `restartServer()` and `stopServer()` may shut down gracefully and record the run as stopped, so S-H7-40 needs a hard kill of the server process (and of the fake provider child) to reach START_UNKNOWN through the real lifecycle, not by writing database rows.
- The quota warning (`verify-m4-browser.mjs` checks VM4-04 and VM4-06) needs provider usage data at 5% remaining.
  Usage for Grok comes from the provider's own network billing API, which has no loopback seam, so the real Agents page cannot show a quota warning in T1 today (S-H7-48).
  The existing T0 test `usage.test.tsx` covers those checks at markup level only.
- The Agents header stats sit in a container hidden below the `sm` breakpoint (640px), so the "-0 AVAILABLE" defect can only be observed at 1440x1000, not at 390x844 (S-H7-50).
- Each header stat renders `dd` before `dt` inside a `div` in a `dl`; axe's `definition-list` and `dlitem` rules are likely to report this on the Agents page (S-H7-20).
  Such a violation is fixed, not listed as an exception, unless the fix is out of scope.
- Playwright's default for a missing snapshot writes the actual image as the new expected file and fails once, so the next run passes.
  That is auto-approval by rerun, which plan section 7 forbids for new screens; S-H7-07 requires the T2 configuration to never write baselines outside an explicit approval step.
- The web app loads Geist fonts through `next/font/google`, which fetches font files at build time.
  A harness build without network, or with a changed font response, renders with fallback metrics and would change every screenshot; S-H7-10 makes that a detected environment failure instead of a wall of diffs.
- `CountUp` formats with `toLocaleString()` and pages show dates, so rendering depends on locale and timezone; the harness browser context pins both (S-H7-10).
- Temporary roots and fixture workspace directories have random paths that the Chat composer, context picker and Workspaces page display; they are masked or given stable names inside the temporary root, and never committed into baselines (S-H7-11, S-H7-28).
- Existing page-driving specs select the Live Telegram panel with the CSS class `div.rounded-md`, which breaks on any restyle; page objects use roles, labels and test ids (S-H7-12).
- Plan section 5 says T2 "runs with T1 by default", but `npm run e2e` runs only the `t1` project and the engineering standards list `e2e:visual` as a separate check (S-H7-29).
- `scripts/verify-contrast.mjs` matches the `scripts/verify-*` glob of plan section 9 but is a static contrast check over `globals.css` with no browser; this table does not retire it (S-H7-49).
- The retired scripts are referenced from `web/package.json` (`verify:m4-browser`), `docs/human-input.md` and the harness plan section 2 row; `docs/telegram-task-control/implementation.md` cites them as historical evidence, which stays as written (S-H7-49).
- Plan section 7 makes baseline approval human for new screens, and every current screen is new to the harness, so H7-done ("approved baselines") needs one operator approval of the initial baseline set.
- Small UI observation, for the implementer to fix separately if agreed: the Pipeline Pause button's tooltip reads as a state ("Paused" followed by "current station will finish") while the pipeline is still playing.

Questions for the operator or reviewer:

- Quota warning in the real app (S-H7-48): add a harness-only loopback seam for a provider's usage API (same pattern and guard as the Telegram base URL) so the warning renders on the real Agents page, or accept the existing T0 markup tests as sufficient for VM4-04 and VM4-06 and retire the script on that basis?
- Themes (S-H7-23): the app has three themes (midnight, deep, daylight).
  Screenshots and axe for every view, state, width and theme is about three times the T2 runtime and may break the 5-minute target.
  Proposal: full QC in the default theme; in the other two themes axe (contrast differs per theme) and overflow on every view at both widths, and screenshots only for Tasks and Agents populated states.
  Accept, or require the full matrix?
- Should `npm run e2e` run T1 and T2 together, as plan section 5 says, or stay T1 only with `e2e:visual` as a separate required check, as the engineering standards say?
- Keep `scripts/verify-contrast.mjs` (not a browser script), or fold its token contrast check into T0?
