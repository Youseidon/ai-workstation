## How to read this table

Every scenario asserts on up to three layers, named in the Given / when / then cell:
**Phone** is the PhoneDriver transcript (message text, button labels, and, once the driver is extended, message entities; see findings).
**Browser** is Playwright on the Agents page (Task Control settings, Live Telegram panel), Tasks page or Pipelines page.
**Durable** is the REST API (settings, prompt activity with handoffs and remarks, `TelegramLiveStatus`) plus read-only database inspection of `telegram_outbox` payloads, receipts, human responses and runs, plus the Bot API request bodies the harness server sent (`telegramCalls()`).

Tier and backend values: `T0` is a unit or formatter test with no app boot (a temporary root database seeded through public workspace calls, or pure fixtures), or a fake-contract replay; `T1 fake` boots the harness server and web app with the fake Telegram server and the scripted fake agent; `T3 real` runs on the dedicated test bot through the route proxy and the operator's user client; `T1 fake + T3 real` means the same scenario body runs on both backends.
T4 is the operator's phone look check at L3 close-out.

Terms used in the rows:
**Summary** is the output of the F3 model for one task and audience `owner`.
**Card** is the personal question card; **answer card** is the card produced by a reply, with Save answer and Answer and resume; **saved-answer card** carries Resume with saved answer (l1.md).
**Brief fixture** is a READY handoff whose `HandoffBrief` the fake handoff agent returns (see findings); **full brief** means objective, three completed items, 41 passed and 0 failed verification items, one blocker with `requiresHuman` true and a `requiredAction`, one blocker with `requiresHuman` false, two decisions or assumptions, two important files and recommendation `WAIT_FOR_HUMAN`.
**Details** is the collapsed part of the card (decisions and assumptions, important files, full completed list), carried by one `expandable_blockquote` entity.
**UTF-16 length** is the length in UTF-16 code units, which is what JavaScript `length` and Telegram entity offsets count.
**Declared omission** means the card states that a section was shortened or left out (for example "and 12 more in the local app"), as B21 and protocol section 9 require; the exact wording is the implementer's.
Unless a row says otherwise, the common setup is the l1.md setup: harness root with task control, Notifications and Remote actions on, Transport Telegram, one paired operator private chat, a fixture saved task on the fake provider, a `block-on-decision` scenario, workspace, program and suite created through REST with distinct names, and no workstation label override.
Waits are on observable conditions only; "no card" or "no call" is asserted after a later observable event (another card delivered, a status change), never after a sleep.
Every run ends with the token sweep and the real-database-unchanged check.

## Findings from the specification and public interfaces that shape the scenarios

- Card notifications are keyed by question revision, and the public revision of a task (`humanInput.revision` in prompt activity) changes when its latest handoff record changes.
  So a handoff that becomes READY after the first card was sent produces a new card for the new revision, and buttons on the older card become stale.
  This is the natural T1 path to a card with a brief (block, first card from the remark, request a handoff, second card from the brief) and makes "stale revision behaviour unchanged" directly testable (S-L3-A-12).
- The spec's source order puts the latest READY brief before the latest BLOCKER or DECISION_NEEDED remark, with no freshness condition.
  A READY brief from an earlier run can therefore outrank a newer blocker from a later run, and a READY brief recommending `CONTINUE` (whose successor later blocked) would still describe the task.
  B21 says outdated context must not be guessed around; S-L3-F3-04 asserts the literal spec order and records the stale case for question 1.
- "Never truncated" applies to the breadcrumb, blocker and action text, but none of these is bounded: workspace, program and suite names, the label, up to 20 blockers with free-text actions, and a remark of any length.
  Together they can exceed 4096 on their own, and the block form "caps per section" contradicts "never truncated" for blockers.
  S-L3-A-06 asserts what must hold regardless (the card is delivered, stays within the limit, declares what was left out) and question 2 asks for the rule.
- The budget order names breadcrumb, blocker and action, recommendation, completed work and verification, objective, decisions; it does not place the task title line, the "If you wait" line, the reply hint, or the answer text on an answer card.
  An answer card must carry the operator's own reply (up to 4096 characters from the phone) next to the summary, and its buttons submit exactly the bound text; today the preview is clipped at 1500 characters.
  S-L3-A-04 asserts the answer is shown in full or its clipping is declared, and question 3 asks for the priority.
- Protocol section 9 says decisions must not be silently truncated, while the budget shrinks decisions first.
  The rows accept shrinking only with a declared omission (S-L3-A-05).
- "Program/suite, pipeline step x/y" does not say which pipeline counts: the suite flowchart (`SuitePipelineView.steps`, the enabled rules in step order) or a named pipeline (`PipelineRecord.stages`, suites in sequence).
  It also does not say whether the position shows when the task is on a flowchart but no pipeline run is active.
  S-L3-F3-06 uses the suite flowchart for the fixed cases and records the others for question 4.
- The "If you wait" line is "derived from the pipeline rule", but only one wording exists (user-flows section 2: this task and its pipeline stay paused; other workspaces continue).
  The rule has four `onBlocked` values, pipelines can be WAITING_HUMAN, PAUSED or STOPPED (`retry_exhausted`, `recover_exhausted`), a saved answer holds the pipeline (`human_response_saved`), and a task can have no pipeline.
  S-L3-F3-07 asserts determinism and independence from task text for every case, and question 5 asks for the wording table.
- `sanitizeTelegramText` keeps "the existing secret and localhost redaction", which misses common forms: GitHub tokens use `ghp_` (the pattern expects `ghp-`), `Authorization: Bearer <token>` (the form the Progress API prompt uses), Telegram bot tokens (`<digits>:<35 characters>`), and localhost without a scheme (`localhost:4000/api`) or as `0.0.0.0`.
  The line and block forms now reach far more agent-written text (briefs, decisions, important files).
  S-L3-F3-10 pins the existing patterns as must and lists the gaps as expected-redacted pending question 6.
- Whether the details section is also shown to non-owner audiences, and whether the owner card should show account quota, is out of scope: the F3 field list has no quota field and `audience` has one value.
  S-L3-F3-12 asserts only that the hook refuses anything but `owner`.
- `PhoneMessage` has `text` and `buttons` only, so no phone-layer assertion can see the expandable blockquote.
  Needed extension, identical on both backends: `entities: Array<{ type: string; offset: number; length: number }>`, mapping GramJS `MessageEntityBlockquote` with `collapsed` true to `expandable_blockquote` and keeping the auto-detected types (`url`, `mention`, `hashtag`, `bot_command`) that real Telegram adds without any `parse_mode`.
  Rows S-L3-A-01, 07, 08, 09 and 10 depend on it.
- The fake Telegram server stores any `entities` array without validation, never rejects `parse_mode` misuse, and does not model real Telegram's handling of leading or trailing whitespace; its 4096 check uses JavaScript length.
  Whether real Telegram counts the 4096 limit in UTF-16 code units, rejects an entity running past the text end, rejects an unknown entity type, or shifts offsets when it trims whitespace is unverified.
  S-L3-A-09 records these on the test bot and makes the fake follow the recordings.
- The fake provider has no way to produce a READY handoff brief by intent: the handoff run takes the next queued scenario and the `done` behaviour on a prompt with neither the live nor the inline markers ends with `scenario.text`, which may happen to parse as a brief.
  Needed: an explicit `handoff-brief` behaviour with a typed `brief` object (including malformed and oversized variants) that logs that it ran as the read-only handoff run, so a scenario proves the brief came from `POST /api/prompts/:id/handoff` and not from the execute run.
- The fake provider posts only `DECISION_NEEDED` remarks on the live path and none on the inline path.
  Needed: a `remarkKind` option (`BLOCKER` or `DECISION_NEEDED`), a sequence of remarks of mixed kinds in one run (to test "latest" ordering against newer PROGRESS, FINDING or VERIFICATION remarks), and a way to block with no remark at all.
  No REST route lets the harness post an agent remark directly, so these must come from the fake agent.
- The L1 scenarios and harness helpers locate cards by the first line "Task needs input: <title>" (`QUESTION_PREFIX`, `telegramFlows.ts`, `l1Live.ts`, and the H1 leftover-card check), and assert "Your answer:\nRed", "Saved answer:\nBlue" and "Reply to this message with your answer.".
  User-flows section 2 starts the card with the breadcrumb and "Task: <title>", so slice A breaks those locators without any behaviour regression; S-L3-A-22 needs the operator's agreement to change the locator helpers only (question 7).
- Real Telegram turns `/task`, `@name`, `#tag` and URLs in plain text into tappable entities even without `parse_mode`.
  A blocker or decision containing "/help" becomes a tappable command once slice B exists; this is not markup injection, but S-L3-A-10 records it for the look check.
- F3 has no phone-visible output of its own until A renders it (or B's `/task`); F3's T1 evidence is therefore limited to the workstation label setting and the L1 regression, and everything else about the model is T0.

Questions for the operator:

1. Stale briefs: should a READY brief be used when a BLOCKER or DECISION_NEEDED remark, or an execute run, is newer than the brief's completion?
   Recommendation: use the brief only when it is newer than the latest execute run's start; otherwise fall back to the remark, so the card never describes an earlier blocker (B21).
2. When the never-truncated parts (breadcrumb, title, every human blocker and its required action) exceed 4096 on their own, what happens: a per-blocker cap with a declared omission, only the first blockers with "and N more in the local app", or a continuation message?
   Recommendation: keep every blocker description and action whole up to a per-item cap, list as many as fit, declare the rest; never split one card into two messages, since replies bind to one message.
3. Where do the task title, the "If you wait" line and, on answer and saved-answer cards, the operator's answer text sit in the budget order?
   Recommendation: title and "If you wait" with the breadcrumb (never truncated, title capped); the answer text above recommendation, shown in full up to Telegram's limit because the buttons submit exactly that text.
4. Pipeline position: suite flowchart step, named pipeline stage, or both ("stage 2/3, step 3/5")?
   Should the position show when the task is on a flowchart with no active or waiting pipeline run?
5. Wording of the "If you wait" line for: no pipeline; `wait` with the pipeline WAITING_HUMAN; retry exhausted and waiting; recover exhausted with the pipeline STOPPED; the pipeline PAUSED by the operator; a saved answer holding the pipeline.
   Should "other workspaces continue" also mention other pipelines in the same workspace?
6. Redaction: widen the shared patterns in F3 to cover `ghp_`, bearer tokens, Telegram bot tokens and scheme-less or `0.0.0.0` localhost, or keep exactly the existing patterns as the plan says?
   Recommendation: widen now, since F3 multiplies the agent text that reaches the phone.
7. May the implementer change the L1 card locator helpers (the "Task needs input:" prefix and the answer and saved-answer text checks) as part of A, with every L1 row otherwise unchanged?
8. If Telegram rejects a card because of its entities (recorded in S-L3-A-09), should the app resend the same text without entities, or record the card failed and show the error in the Live Telegram panel?
   Recommendation: resend without entities, so the operator still receives the question.
9. Workstation label validation: maximum length, whether an empty or whitespace-only value is rejected or means "use the hostname", and whether characters outside a hostname-like set are allowed (emoji, spaces).
10. Should S-L3-A-20 (a real Claude or Codex handoff brief rendered on the test bot) spend provider quota at L3 close-out, or is the fake handoff agent enough?
