# Scenario table: L3 slice C1 (thread registry and a chat organised without topics)

Status: test-design pass, 2026-09-16, written before implementation.
Review: product-facing, so the operator skims this table and adjusts priorities before implementation starts (harness plan section 12.1).
Scope note: the operator asked for a lean evidence plan for this slice, so this table is deliberately small, like [`l3-a2.md`](l3-a2.md).
It adds no new tier, no new driver capability and no new fake; the pin is observed in the Bot API calls the harness server made, not through a new phone capability.

Specification sources:

- [Engineering plan](../telegram-task-control/engineering-plan.md): RTC-25, and slices C0, C1 and C2 in section 3a.
  C0 is blocked on Telegram (no topics for this bot, and a two-member group cannot become a forum), so C1 organises the flat chat and C2 stays unbuilt.
- [L3 F1/F2 table](l3-f1-f2.md): the outbox edit operation this slice edits the anchor through, and its recorded decisions about a failed edit (recorded failed once, never retried).
- [L3 A2 table](l3-a2.md): the task tag, whose format and function A2 owns; C1 reuses it and never re-derives it.
- [L1 scenario table](l1.md) and [L3 B table](l3-b.md): the rows that must keep passing unchanged.

What changes in the product:

- A `telegram_thread` registry records one row per subject (`task` or `workstation`) per bot and chat.
  Every enqueue resolves its destination through `threadFor(subject)` instead of choosing a topic.
  Topics are unavailable to this bot, so every subject resolves to the paired chat with no topic, which is exactly L1 behaviour, and the Live Telegram panel says so.
- Every message about a task carries that task's tag, the one A2 already renders in the card header, so tapping it filters the chat to that task.
- The first question card for a task is registered as that task's anchor; every later message for the task is sent as a reply to it, so the phone shows the quote header and can jump back.
  Result and receipt messages stay separate replies and are never folded into the anchor: the record of what was decided must not be overwritten by a later edit.
- The workstation subject owns one `/status` control panel, edited in place through the F1 edit path and pinned once.
  Editing rather than resending avoids pin churn, and a pin Telegram refuses is logged and never retried, so it can never fail the message.
- Recovery: if the operator deletes an anchor, the edit of it fails once and is not retried (F1), the registry marks the anchor gone, and the next message for that subject is sent and registered as the new anchor.

## Findings and questions for the operator

1. The plan says the question card is the task's living status, "edited in place through its lifecycle", and that nothing stacks.
   Taken literally, a new card for the same task (a new question revision, an answer card, a saved-answer card) would edit the anchor instead of being sent.
   That is mutually exclusive with rows the operator required to keep passing unchanged: S-L1-05 and S-L1-06 wait for a new answer card message, S-L1-11 waits for a new card when the question changes, S-L3-A-01, S-L3-A-02 and S-L3-A2-11 wait for a new card once a handoff brief arrives, and S-L1-09, S-L1-10 and S-L1-13 tap buttons on older cards that an edit would strip.
   This slice therefore registers the first card as the anchor, sends every later card as a reply to it, and edits only the workstation control panel in place.
   ANSWERED by the operator 2026-09-16: the reply chain is the intended organisation. Later cards do not edit the anchor, the eight rows stand, and the plan's wording was amended. A task's live status becomes a separate status message per task in the queued follow-up.
2. The same tension applies to `/status`: one panel edited in place, versus the B rows that send `/status` several times in one chat and wait for a new message each time.
   This slice keeps the command's own reply and additionally refreshes the pinned panel in place, so no B row changes.
   ANSWERED by the operator 2026-09-16: `/status` keeps answering with its own message. A typed command that produces no reply reads as broken; the pinned panel is the standing view.
3. Telegram's current Bot API expresses a reply as `reply_parameters`; `reply_to_message_id` (with `allow_sending_without_reply`) is the older form the plan names and Telegram still accepts.
   This slice sends the form the plan names, and the fake mirrors it.
   A T3 recording should confirm both forms before C2, in the same way the topic fields are recorded.
4. No new human-verification row is proposed: H-L3-02 already covers a deleted message, and the phone look check at L3 close-out covers the tag, the replies and the pin.
