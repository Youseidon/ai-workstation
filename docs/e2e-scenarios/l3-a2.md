# Scenario table: L3 slice A2 (a card the operator can decide from)

Status: test-design pass, 2026-09-16, written before implementation.
Review: product-facing, so the operator skims this table and adjusts priorities before implementation starts (harness plan section 12.1).
Scope note: the operator asked for a lean evidence plan for this slice, so this table is deliberately smaller than [`l3-f3-a.md`](l3-f3-a.md).
It adds no new tier, no new driver capability and no new fake.

Specification sources:

- [Engineering plan](../telegram-task-control/engineering-plan.md): RTC-22 and RTC-23, and slice A2 in section 3a.
- [Human verification checklist](../telegram-task-control/human-verification.md): the phone look check of 2026-09-16, which is the origin of this slice; H-L1-05 and H-L1-18 are the regression baseline.
- [L3 F3/A table](l3-f3-a.md): the summary model, the card budget, the sanitization rules and the fixtures these rows reuse.

What changes in the product:

- The card is rendered in labelled sections, ordered so that a phone shows the identifier and breadcrumb, the question and its required action, the options with their trade-offs, and the recommendation before anything is collapsed.
- The summary gains three facts: the task's identifier and age, the next enabled step of the suite flowchart, and the task's history (runs, when it blocked, how many times, and previous answers).
- The agent progress contract gains an optional list of options, each a label with its advantages and disadvantages.
  Options are reported by the agent, never generated while rendering: a card must not wait on a model, and a trade-off the agent never considered must not appear on the phone.

## Findings and questions for the operator

1. Options belong to the blocking status, not to the task: a later block replaces them.
   Confirm that a stale option list must never survive into the next question.
2. History is capped for the phone (proposal: the last three runs and the last previous answer, with a count of the rest).
   The local app keeps everything.
3. Age is rendered as "blocked 14 min ago" from the block time, not the run start.
   Cards are not edited as they age, so the age is the age at delivery; F1 edits refresh it when the card is edited for another reason.
4. The identifier shown is the task key the `/task` command already accepts, so that reading a card and asking for it later use the same word.
5. No new human-verification row is proposed: the existing phone look check at L3 close-out covers this card, and its 2026-09-16 result is the reason this slice exists.
