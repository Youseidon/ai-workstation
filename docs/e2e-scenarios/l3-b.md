## How to read this table

Every scenario asserts on up to three layers, named in the Given / when / then cell:
**Phone** is the PhoneDriver transcript (messages, edits with their `edited` flag and text history on the fake, button labels, callback data on the fake, toasts).
**Browser** is Playwright on the Tasks, Pipelines or Agents page (Live Telegram panel, provider usage).
**Durable** is the REST API (`GET /api/operations`, `/api/pipelines`, `/api/providers/usage`, `TelegramLiveStatus`, prompt APIs) plus read-only database inspection (receipts, actions, human responses, runs, start intents, outbox rows, inbox rows) plus the Bot API calls the harness server made (`telegramCalls()`) and the fake provider log.

Tier and backend values: `T0` is a unit or stubbed-HTTP test with no app boot; `T1 fake` boots the harness server and web app with the fake Telegram server and the scripted fake agent; `T3 real` runs on the dedicated test bot through the route proxy and the operator's user client; `T1 fake + T3 real` means the same scenario body runs on both backends.
T4 is the operator's phone look check at L3 close-out.

Terms used in the rows:
**View** is a message produced by a section 9 command or by a navigation tap; **view button** is a button on a view.
**Nav tap** is a tap on a button whose callback data starts `nv_`.
**One edited message** means the phone shows the same message id before and after, with `edited` true and no new bot message in between.
**No side effects** means, comparing durable state before and after: row counts of `task_control_action`, `task_control_receipt`, human responses, runs and start intents unchanged; every prompt's status, revision and pipeline run state unchanged; settings unchanged; zero fake provider spawns; zero provider usage refresh forced by the view; the only new outbox rows are sends or edits addressed to the operator's chat.
**Status fixture** is: workspaces `alpha` and `beta`; in `alpha` one task each in WORKING (`hang-until-stopped`), AWAITING_RESPONSE with a READY handoff brief, AWAITING_RESPONSE with a BLOCKER remark only (`block-on-decision`), RECOVERY_NEEDED (`crash-after-spawn`), FAILED (`fail`), READY (saved, never run), WAITING_DEPENDENCY, COMPLETE (`done`) and SKIPPED; in `beta` one AWAITING_RESPONSE and one READY task; a three-step fixture pipeline in `alpha` playing at step 2; provider usage for the fake provider as decided in question 1.
Unless a row says otherwise, the common setup is the l1.md setup (harness root with task control, Notifications and Remote actions on, Transport Telegram, one paired operator private chat) with the status fixture.
Every view assertion compares against `GET /api/operations` read in the same step, never against hard-coded counts alone.
Waits are on observable conditions only; "no reply" and "no further call" are asserted after a later observable event (a probe command from the paired operator is answered), never after a sleep.
Every run ends with the token sweep and the real-database-unchanged check.

## Findings from the specification and public interfaces that shape the scenarios

- The plan defines each view as a pure function over `OperationsSnapshot` plus F3, but neither carries quota: `/quota` and the `/status` quota headline need `ProviderUsage` (today `GET /api/providers/usage`, which may fetch from provider account APIs).
  The harness has no seam that makes the fake provider report usage, fail a usage fetch, or age a figure (question 1).
- `/tasks done` "covers the last 24 hours", but `OperationsPrompt` has no completion time, only `lastActivityAt`, and the harness has no clock seam for task timestamps.
  S-L3-B-06 needs both a defined source and a way to place completions at 23 h and 25 h (question 2).
- The filter names do not map one to one onto `PromptOperationalState`: `running` is presumably WORKING, `recovery` RECOVERY_NEEDED, `failed` FAILED, `ready` READY, but `blocked` may or may not include WAITING_DEPENDENCY, and `done` may or may not include SKIPPED (user-flows 6 says skip never means success).
  The `/status` counts must use the same mapping (question 3).
- Plain text from the paired operator today gets "To answer a task, reply to its question message...", and slice B replaces that with `/help`.
  `e2e/tests/t1/h3-fake-telegram.spec.ts` waits for the old text, and S-L1-12 asserts that no bot reply to stray text carries any button; if `/help` has view buttons, S-L1-12 fails.
  Both need an agreed edit before implementation, per the rule that L1 scenarios are not edited without the operator (question 4).
- Parsing commands before the reply-to check means a reply to a question card whose text starts with `/` is a view request, never an answer.
  Whether that applies to any `/word` or only to registered commands decides whether an answer such as "/usr/local is fine" can still be given from the phone (question 5).
- Pairing (`/start <code>`) is matched before the actor check today and must stay so, since an unpaired chat must be able to pair; `/start` without a code from the paired operator is not in section 9, so it falls to `/help` as an unknown command.
- Section 9 does not say what `/tasks <unknown>`, `/task` with no argument, upper-case commands or `/status@otherbot` produce (question 6).
- For a navigation tap from a stranger or unpaired chat, section 9 says "ignored as for other messages", but a callback left unanswered leaves a spinner on the stranger's client, and L1 answers stranger `tc_` taps with a rejection toast.
  S-L3-B-23 requires no edit, no content and no identifier in any toast, and accepts either no answer or an empty one.
- Protocol 7a says the navigation hook edits "the message"; nothing limits that to view messages.
  A crafted `nv_` callback (possible through MTProto, and through `userTapsButton` on the fake) against a question card or answer card would replace the card and strip its buttons.
  S-L3-B-18 asserts cards are never overwritten by navigation (question 7).
- The fake's `setMyCommands` accepts any array; real Telegram validates command names (lower-case letters, digits and underscore, 1 to 32 characters) and description length.
  The fake also does not enforce the 64-byte `callback_data` limit or an inline keyboard size limit, and has no `getMyCommands`; `PhoneDriver` has no way to read the bot's command menu or to tap with crafted callback data on T3.
  S-L3-B-30 records real fixtures and asks for those fake and driver additions.
- A callback query older than about 15 seconds can no longer be answered on real Telegram, so after a restart or outage the toast is absent on T3 while the edit must still happen; the failure to answer must not put the runtime in backoff or block the edit.
- `task_control_receipt.action_ref` must reference a stored action, so "never produces a receipt" is asserted as unchanged row counts of both `task_control_action` and `task_control_receipt`, and additionally as zero view buttons whose data starts `tc_`.
- User-flows 9 says an oversized view is paginated, while slice A (which `/task` shares) shrinks lower-priority sections to fit and never truncates breadcrumb, blocker or action text; the two rules differ for `/task` (question 8).
- "Inside a task topic, `/status` describes that task" needs C1 and C2 (a private-chat actor is not authorized in any topic until C2), so S-L3-B-40 is blocked on C2 rather than skipped.
- Whether views answer while Remote actions or Notifications are off is not specified; views are read-only, so the recommendation is that they answer whenever task control is enabled and the actor is paired (question 9).
- "as of HH:MM" does not name a time zone (question 10).
- `OperationsPrompt.workspace.workDirectory` is an absolute local path in the snapshot; nothing says whether views may show it.
  S-L3-B-39 treats it as not shown, matching the "no localhost detail" spirit of user-flows 1 (question 11).

Questions for the operator:

1. Quota source and harness seam: should the view registry take `ProviderUsage` (last cached figures, never a forced refresh) alongside the snapshot, and may the harness add a usage seam (under `AGENT_CONSOLE_HARNESS=1`) so the fake provider can report fresh, stale, failed and absent figures?
2. `done` in the last 24 hours: which timestamp defines completion, and may the harness set task completion times through a clock or fixture seam?
3. Filter mapping: does `blocked` include WAITING_DEPENDENCY, and does `done` include SKIPPED (shown as skipped, not success)?
4. May `h3-fake-telegram.spec.ts` and S-L1-12 be edited so plain text expects `/help`, and may `/help` carry view buttons (S-L1-12 would then assert "no `tc_` buttons" instead of "no buttons")?
5. Should only registered commands take priority over a card reply, with any other `/text` reply still treated as an answer?
   Recommendation: registered commands only, so answers starting with a path still work; unknown commands outside a card reply still get `/help`.
6. What do `/tasks <unknown filter>`, `/task` with no argument, `/STATUS` and `/status@otherbot` produce?
   Recommendation: filter buttons for an unknown filter, the task picker (or `/help`) for a bare `/task`, case-insensitive commands, and silence for a command addressed to another bot.
7. May the navigation hook edit only messages the bot sent as views, answering a crafted `nv_` on any other message with a toast and no edit?
8. For `/task` over 4096 characters: slice A's priority budget (identical to the card) or pagination?
   Recommendation: the card budget, with pagination only if breadcrumb, blocker and action text alone exceed the limit.
9. Should views answer while Remote actions are off, and while Notifications are off?
10. "as of HH:MM": workstation local time or UTC, and should a date appear when the snapshot is not from today?
11. May views show workspace directories, or only workspace names?
