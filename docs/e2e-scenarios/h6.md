## How to read this table

Covers uses harness plan section references, as in [h0-h4.md](h0-h4.md): `3-P3` is accuracy principle 3, `4.1-guard` is the guard list in section 4.1, `4.2-real`, `4.2-userphone` and `4.2-proxy` are the real backend, `TelegramUserPhone` and route proxy parts of section 4.2, `6.2-telegram` is the Telegram row of section 6.2, `7-look` and `7-setup` are rows of section 7, `11-drift`, `11-interfere`, `11-flaky` and `11-session` are rows of the risk table, and `H6-done` is the slice's definition of done in section 9.
Tier T0 means a unit or contract test of a harness piece or a server seam, with no app boot and no network beyond loopback.
Tier T1 means the scenario boots the harness server and web app on a temporary root with the fake Telegram backend.
Tier T3 means the real test bot on real Telegram, through the route proxy, with the operator's user client; T3 rows run under `npm run e2e:live` only.
T4 is a human check (plan section 7).
Backend is `fake`, `real` or both; `T0 fake + T3 real` means the same assertions run on both backends.

Terms used in the rows:
**Live file** is `~/.config/ai-workstation/e2e-live.env` with the keys `E2E_TELEGRAM_TEST_BOT_TOKEN`, `E2E_TELEGRAM_API_ID`, `E2E_TELEGRAM_API_HASH`, `E2E_TELEGRAM_USER_SESSION`, `E2E_TELEGRAM_TEST_BOT_ID`, `E2E_TELEGRAM_TEST_BOT_USERNAME`, `E2E_TELEGRAM_OPERATOR_BOT_ID` and `E2E_TELEGRAM_OPERATOR_USER_ID`.
**Bot probe** is a minimal Bot API caller inside a driver contract test, using the test bot token through the route proxy, with no harness server running so nothing else polls the test bot; it plays the bot side so `TelegramUserPhone` can be checked without the app.
**Blocked on setup** is a reported outcome distinct from pass, fail and skip: the run exits non-zero, and every affected T3 row ID is listed as blocked with the reason.
Every T3 run implicitly ends with the token sweep (including the live secrets), the real-database-unchanged check and the operator-app check of S-H6-19; rows that name those checks test them.

## Findings from the plan and existing interfaces that shape the scenarios

These are facts the implementing agent must respect, or flag if the plan disagrees.

- The server guard today is a denylist: `assertNotOperatorBot` refuses ids in `AGENT_CONSOLE_HARNESS_FORBIDDEN_BOT_IDS` and accepts any other bot.
  Plan 4.1 asks for refusing "the operator's own bot rather than the registered test bot", so a real-backend run also needs a positive check against `E2E_TELEGRAM_TEST_BOT_ID`; S-H6-17 and S-H6-18 assert both, and neither may rely on the token.
- `operatorBotId()` in the orchestrator falls back to parsing the token prefix from the repository `.env` when the live file has no operator bot id, and the sign-in tool writes an empty `E2E_TELEGRAM_OPERATOR_BOT_ID` when the repository `.env` is missing.
  Plan 4.1 says the guard never reads the repository `.env`; the runner reading it is a different process, but an empty or missing operator id silently yields an empty denylist.
  S-H6-17 makes that case blocked on setup instead.
- The Telegram cursor is stored per temporary root (`workspaces.telegramCursor(botId)`), so every fresh harness root starts polling the shared test bot at offset 0 and receives every update left pending from earlier runs (Telegram keeps undelivered updates for about 24 hours).
  The sign-in tool itself leaves one such update, the `/start` it sends.
  S-H6-21 and S-H6-22 cover this.
- In private chats Telegram numbers messages per account: the id the user client sees for a bot message differs from the `message_id` the bot got from `sendMessage`, and the user's counter also advances with the operator's unrelated chats.
  On the real backend `PhoneMessage.id`, `replyToId`, `cursor()` and `afterId` are therefore phone-side ids: monotonic, not contiguous, and never comparable with durable outbox or receipt message ids.
  The existing `h3.contract.test.ts` asserts id arithmetic (`sent.messageId + 1`) that holds only on the fake; no scenario that runs on both backends may do that (S-H6-06).
- `PhoneDriver.messages()` does not say whether it returns the whole chat or only this run's messages.
  The fake starts empty per run, while the real private chat keeps every earlier run's cards and the operator's own messages.
  S-H6-07 requires identical semantics on both backends; the operator or implementer must pick which (recommendation: scoped to messages newer than the environment's start).
- The fake accepts callback answers for 15 minutes (`callbackAnswerWindowMs`), while l1.md's findings say real Telegram stops accepting them "some seconds" after the tap.
  These disagree, and S-L1-14 depends on the answer; S-H6-09 measures the real window and whichever side is wrong gets fixed.
  Resolved 2026-09-15 by the first T3 run: real Telegram refuses answers about 15 seconds after the tap (sent 13s after the bot received the update: accepted; 14s: refused), so the fake's window is now 15 seconds.
- `FakePhone.tap` waits 15 seconds for a toast, while a real user client's callback request ends with Telegram's own bot-response timeout; the bound must be documented and close enough that a scenario written against one backend does not time out on the other (S-H6-04).
- The fake ignores `allowed_updates`, while the real client asks only for `message` and `callback_query`, so real Telegram never delivers `edited_message` to the app.
  The fake's `edited_message` injection in S-L1-09 is a T1-only case and must not be ported to T3; the contract recording records only allowed update types (S-H6-28).
- The fake's `setOutage("hang")` never processes a hung request, so a hung `sendMessage` has no effect.
  A proxy that forwarded requests upstream while withholding responses would instead be a lost-response fault with real side effects (a duplicate card on retry), so the hang variant must not forward (S-H6-13).
- The sweep matches exact byte strings of at least 8 characters.
  A token that appears URL-encoded (`%3A` for the colon), JSON-escaped, or only as its secret half after the colon, and a session string that appears decoded, would not match; S-H6-25 asks for those forms.
- `dispose()` checks only that ports 4000 and 3000 still accept connections.
  "The operator's app keeps polling its own bot undisturbed" (H6-done) needs a stronger read-only observation of the operator's status API (S-H6-19).
- The live file does not exist on this machine yet (checked 2026-09-15), so the one-time setup (S-H6-32) is outstanding and every T3 row would be blocked on setup today.
- Forum topic methods may not be available in a private chat with a bot on real Telegram; the contract recording records whatever real Telegram returns and lists any method it could not record rather than inventing a fixture (S-H6-28).

Questions for the operator:

- Burn-in (principle 6, risk 11-flaky) applied to S-L1-15 on T3 means 20 real 10-minute expiries, over 3 hours.
  Accept that cost at milestone close-out, burn in the T3 driver and proxy rows only, or burn in S-L1-15 on T1 and run it once on T3?
- Should a missing `E2E_TELEGRAM_OPERATOR_BOT_ID` be allowed when the repository `.env` has no token at all (no operator bot exists), or always be blocked on setup?
