# Scenario tables: harness slices H0 to H4

Status: test-design pass, 2026-09-14, written before implementation from [the harness plan](../e2e-harness-plan.md) and existing public seams only.
Review: harness-internal slices, so the review pass checks these tables instead of the operator (plan section 12.1).

## How to read these tables

Covers uses harness plan section references: `3-P5` is accuracy principle 5, `4.1-guard` is the guard list in section 4.1, `6.2-ports` is the ports row of section 6.2, and `H2-done` is the slice's definition of done in section 9.
Tier T0 means a unit or contract test of a harness piece or a server seam, with no app boot.
Tier T1 means the scenario boots the harness server and web app on a temporary root.
All T1 scenarios in these tables use the fake Telegram backend or no Telegram at all; none uses real Telegram.
Every T1 scenario implicitly ends with the token sweep and the real-database-unchanged check; rows that name them test those checks themselves.

## Findings from the existing seams that shape the scenarios

These are facts from current code that the implementing agent must respect, or flag if the plan disagrees.

- `server/src/config.ts` loads `.env` and `server/.env` from `AGENT_CONSOLE_REPO_ROOT`, but `dotenv` never overrides variables already in the process environment.
  A harness server that inherits the operator's shell environment could still pick up a real `TELEGRAM_BOT_TOKEN`, so S-H1-06 checks the spawned process environment, not only the file.
- `web/next.config.ts` loads `../.env` unconditionally and defaults `NEXT_PUBLIC_AGENT_SERVER_URL` to port 4000, so a harness build that forgets the variable silently talks to the operator's server (S-H1-05, S-H1-07).
- `HttpTelegramBotApi` maps error codes as follows: 429 to `rate_limited` using `parameters.retry_after` (1 second default), 401 and 404 to `unauthorized`, 409 to `conflict`, 5xx to `transient`, and everything else, including 400 and 403, to `rejected`.
  The fake must produce envelopes that drive each of those branches; the plan's "403" is a `rejected` case, not an auth failure.
- The plan's "FAILED" outcome for the fake provider has no prompt status of that name.
  A provider process that exits non-zero or dies ends the run in state `ERROR`, and `finishAgentRun` moves a still `IN_PROGRESS` prompt to `BLOCKED` with a `SYSTEM` status event saying the process ended without a DONE or BLOCKED status.
  The H2 tables use "FAILED" to mean that observable result.
- Detection runs `<binary> --version` and uses the first line of stdout (or stderr); Grok availability also requires `XAI_API_KEY`, `GROK_ASSUME_AUTHENTICATED` or a stored `auth.json` under `GROK_HOME`.
  The harness must satisfy the auth check through the temporary root settings or a temporary `GROK_HOME`, never through the operator's `~/.grok`.
- The inline path is chosen when `savedPromptExecuteReachabilityProblem` returns a problem: Host access off and Grok sandbox mode not `off` (or Codex sandbox not `danger-full-access`).
  `parseOfflineAgentStatus` accepts DONE only with a `verificationSummary`, and BLOCKED only with both `reason` and `verificationSummary`; anything else is ignored and the prompt falls to the system BLOCKED result.
- The runtime already accepts `now` and `pairingTtlMs`; the action TTL default lives in `taskControl.ts` (10 minutes), the quota freshness default in `quotaAdvisor.ts` (10 minutes), and the poll timeout in `TELEGRAM_POLL_TIMEOUT_SECONDS` (25 seconds).
  None is currently configurable from the environment, so H4 adds the seams and S-H4 rows pin both the harness values and the unchanged defaults.
