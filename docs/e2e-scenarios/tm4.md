## Scope and fixed decisions

TM4 adds handover on an existing item thread.
A requester who needs help finishing a work item captures it, pushes a feature branch and opens an offer in the item thread; a teammate accepts, checks out the branch, works on it with their own workstation, their own settings, their own provider login and their own quota, and hands the item back.

**The lifecycle is not redefined here.**
[protocol.md](../telegram-task-control/protocol.md) section 5 is authoritative for every state, authorized actor and required condition, and H02 builds that table rather than a summary of it.
An earlier draft of the handover rules invented a six-state machine and a `RELEASED` state and was withdrawn; no row below reintroduces either.

**The offer is an open call.**
It names no receiver, any available teammate may accept, and the first accept wins by the shared update rather than by which tap reached a bot first.
B17, R-A, RTC-11 and protocol.md were all amended on 2026-09-20 to match.
The control record is therefore the arbiter of a simultaneous accept, which is why H02 precedes H03 and why the record must exist before an offer does.

**There is no release action and no `RELEASED` state.**
A receiver who cannot finish uses `return_work`, the result is labelled partial, and that is what releases the executor.
TM4's migration adds exactly seven actions: `publish_offer`, `accept_offer`, `decline_offer`, `withdraw_offer`, `return_work`, `apply_result` and `request_changes`.
No row below asserts an eighth.

**Neither Git record exists yet.**
`refs/aw/items/<item>/control` and `aw/handover/*` are referenced nowhere in `server/src`; the only Git-carried record built today is the roster `refs/aw/team`, and `item_link.control_head` is a placeholder column that no caller ever writes.
Every repository assertion below is therefore a new-behaviour assertion, not a regression one.

TM4's migration is **number 29 or later**: F02 took 27 and F07 took 28.

TM4 excludes, deliberately, so no row assumes them: a third team member, further handoff beyond a return to the requester, remote Stop across workstations, package signing and device keys, and any hosted relay.
A receiver returning partial work is a return to the requester, so it stays inside the boundary; a requester stopping a receiver's run from their own phone is remote Stop, so it does not.

The accepted defaults stay unchanged.
A Team action expires after 10 minutes.
Grants end when handover starts.
The shared-record read interval is the recorded 5-second default.
`team.enabled` stays false by default and these scenarios enable it explicitly in both environments; handover stays behind its own disabled capability until G02's evidence half, RTC-12's capability matrix, is produced inside H04.
This table deliberately does not choose the capability's setting key, a control-record polling interval other than the recorded default, an offer deadline value, or a credential-shape detector.

The F track's fixes are load-bearing here and rows assert against them rather than around them: a closed item refuses every action (F02), a supergroup upgrade repairs itself before anything else is processed (F05), anchor writes are bounded and compared on material content (F07), and a completed anchor renders from the completed state and retires only once its run has ended (F08).

### One unsettled point: the control record's ref namespace

Two authoritative documents disagree, and H02 cannot build both.

| Source | Says the control record lives at |
| --- | --- |
| [protocol.md](../telegram-task-control/protocol.md) section 4 | `aw/control/<task-id>`, an ordinary branch under `refs/heads/` |
| [teammate-design.md](../telegram-task-control/teammate-design.md) section 6, [handover-rules.md](../telegram-task-control/handover-rules.md), the H02 task row and G04 in [implementation.md](../telegram-task-control/implementation.md) section 6d | `refs/aw/items/<item>/control`, a custom ref outside `refs/heads/` |

These are different namespaces with different host-protection behaviour, so the choice changes what the compare-and-swap rests on, what the host's branch protection covers, and what G04's retention rule points at.

**This table is written against `refs/aw/items/<item>/control`, and TM-T0-6 names the conflict in the row where it decides the assertion.**
Three reasons.
First, teammate-design.md section 6 already states the decision procedure and its fallback: the custom ref is used if the host rejects a non-fast-forward update of a ref outside `refs/heads`, and only "if it does not hold, the record moves to an ordinary branch `aw/control/<item>`".
Second, that condition was tested and passed.
LG-1, recorded as H-TM-LG1 on 2026-09-17, pushed and fetched `refs/aw/*`, had a divergent non-fast-forward update rejected and triggered no Actions run, which is exactly the custom-ref case and not the `refs/heads/` one; `refs/aw/team` has shipped on the strength of it since TM1.
Third, protocol.md section 4 keys its layout to `<task-id>`, which predates TM2's item identity, while every later document keys the record to `<item>`, which is what `item_link` and the group tags are built from.
Taking protocol.md's branch would also put handover state inside the product branch namespace the remote protects for code, which G04's "keep the records, delete the branches" rule deliberately separates.

If jd rules the other way, TM-T0-6 is the only row that changes, and it changes in its ref names and its host-rejection assertion rather than in its behaviour.
**H02 must not start until jd settles this.**

## Observable layers

- **Phone/group:** the offer card in the item thread naming no receiver, the receiver's own bot posting its Accept and run card, the capture preview with its file list and flagged credential shapes, anchor progress, the loser's inert card and the reason it gives, completion and review cards.
- **Transport:** each bot's delivered updates and Bot API calls under LT-1 broad administrator delivery, receipts answered promptly, edits coalesced, and no output from a workstation that owns nothing.
- **Durable:** migration 29 schema, the seven actions, action references and applied-once receipts, `item_link` with `control_head` written and read, local task and run rows, and the caches that must defer to the record.
- **Repository:** the `aw/handover/<item>` branch, the control record's `state.json` and `events/<command id>.json`, single-parent commits, fast-forward or rejection only, no force-push ever, and no token, path or credential in any ref.
- **Execution:** exactly one workstation runs the item at a time; the receiver runs in its own worktree under its own provider login and its own approved policy; a refusal starts nothing and leaves no orphan worktree.
- **Browser:** the handover surface stays hidden while the capability is disabled, personal controls remain available, and the requester's pipeline hold is visible until the work is applied or the handover ends.

## Proposed rows this table recommends jd change

Every **Ruled** row in [handover-rules.md](../telegram-task-control/handover-rules.md) is written into the rows above as settled.
The H01 card asks for any **Proposed** row that should change, and four should.
None of them blocks H02 from starting.

1. **4.2, "Nobody accepts, indefinitely".** The row says the offer never expires on its own. That contradicts protocol.md, which gives the Offer record a **start deadline**, defaults an approval deadline to 24 hours, and lists **expire** on the `OFFERED` to `WITHDRAWN` transition. Since protocol.md's table is authoritative, an offer should carry a deadline and expiry should move it to `WITHDRAWN`, leaving the requester free to re-offer. What genuinely does not expire is the requester's ability to publish again, and the 10-minute action expiry remains a property of the card rather than of the offer. TM-T0-6 asserts that transition without an expiry case today; adding one is a one-line change to that row.
2. **4.4, "Requester's task is completed locally while claimed".** The row says the receiver's "run is stopped". As written, that is remote Stop across workstations, which section 5 of the same document lists as **deliberately excluded**, and it contradicts ruling 4 and B20, under which only the current executor acknowledges physical stop or release. It should read that the requester's completion records a **cancel request**, the receiver's workstation stops its own run and acknowledges, and the item is not closed until it has; the branch is still kept until the requester deletes it. TM-T1-H2 is written to the corrected form, since the uncorrected form would require a mechanism TM4 does not build.
3. **4.3, "Receiver declines".** Its outcome is still marked Proposed and still offers the alternative "or returns to the requester as unclaimed under a named one". Ruling 1 removed the named receiver, so half this row describes a design that no longer exists. It should settle as: the decline is recorded per person, that person's card goes inert, the offer stays `OFFERED` for anyone else, and the requester is shown that it is unclaimed once every current roster member has declined, without auto-withdrawing.
4. **4.5, "Apply while the item was closed by `/close`".** Refusing is right and follows F02, but it leaves a way to strand completed work: closing an item while a receiver holds or has returned it discards that work with no path back except a new item. The better rule is to **refuse or explicitly confirm `/close` while a handover is live**, so the strand cannot be created, and keep the refusal on apply as the backstop. This is a change to the close path, which F02 owns, rather than to apply.

Three smaller wordings are worth tightening but need no decision.
"Receiver goes silent indefinitely" reads as though nothing can ever end the claim, when protocol.md does give a terminal path through cancellation once no active writer or outstanding start remains.
"Clock skew" says no rule depends on the two machines' clocks, which is right for **ordering** but not for deadlines: the 10-minute action expiry, the 24-hour approval default and protocol.md's five-minute skew block are all time-based, and that matters more if recommendation 1 is accepted.
The size confirmation in 4.1 is better folded into the one capture preview than posted as a second, separate confirmation, so Publish carries at most the flagged-secret confirmation as a distinct tap.
