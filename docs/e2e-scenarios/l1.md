## How to read this table

Every scenario asserts on up to three layers, named in the Given / when / then cell:
**Phone** is the PhoneDriver transcript (messages, edits, button labels, the toast returned by a tap).
**Browser** is Playwright on the Tasks, Agents (Live Telegram panel) or Pipelines page.
**Durable** is the REST API plus read-only database inspection: receipts, human responses, runs, start intents, outbox rows, actors.

Tier and backend values: `T1 fake` runs on the fake Telegram server with the scripted fake agent; `T3 real` runs on the dedicated test bot through the automated user client; `T1 fake + T3 real` means the same scenario body runs on both backends.
Rows marked **LIVE** in the Tier column are the real-Telegram evidence that closes engineering plan step 7 (RTC-20 and the required H-L1 rows in step 7a); per the approved evidence policy they count as live only together with the operator's T4 phone look check.
T1 results on those rows count as automated evidence only.

Unless a row says otherwise, the common setup is: harness root with task control enabled, Notifications on, Remote actions on, Transport Telegram, a token for the backend in use, one paired operator chat, a fixture saved task on the fake provider using the live Progress API path, and a `block-on-decision` scenario that posts a BLOCKER remark and BLOCKED status.
"Consume-answer" means the resumed fake agent asserts the expected answer text is in its context and reports DONE; the assertion failing ends the run in ERROR, so a wrong or missing answer cannot pass silently.
Every run ends with the automatic token sweep and the real-database-unchanged check.
Wherever a row says "no run started", the check is durable (run count and start intents for the prompt unchanged after the receipt is recorded), never a sleep.

## Findings from the specification and public interfaces that shape the scenarios

- Receipts, action references and outbox rows are not exposed by any REST route, so "exactly one receipt" and "no extra outbox row" are read-only database assertions; run counts and human responses are also visible through the prompt APIs and the Tasks page.
- `TelegramLiveStatus` exposes `state`, `lastError`, `nextRetryAt` and outbox counts (`queued`, `retrying`, `failed`), so outage scenarios can assert retry state from the API as well as the panel.
- A tap produces two observable results on the phone: the callback toast (the receipt or rejection) and, separately, a result message.
  Protocol section 7 requires the toast promptly and the application report separately.
- Real Telegram stops accepting an answer to a callback query some seconds after the tap, so after an offline gap the toast cannot appear on the real backend.
  Offline scenarios therefore assert on the result message and durable state, and treat a missing toast as expected on T3; the fake must model the same limit or the fidelity check will diverge.
- H-L1-09 in the checklist says the phone tap is rejected "because the question changed", but a local answer that only saves (without resuming) may not change the question revision.
  S-L1-10 asserts that the phone tap does not apply a second answer in both local variants; if the implementation keeps the revision on a local save, the operator must decide whether that is acceptable.
- The specification does not say what the bot sends for a reply to a message that is not a question card, or a reply to a question card whose task no longer needs input.
  B10 and B12 fix the durable outcome (nothing recorded; reject with current state and fresh choices); S-L1-12 and S-L1-13 assert the durable outcome strictly and accept either no reply or a reply stating the current state without action buttons.
  The operator should pick one before implementation.
- L1 scopes one operator, but nothing prevents pairing a second chat through the same panel.
  The specification does not say whether question cards fan out to every paired chat; S-L1-27 asserts only the safety properties (actions bound to their own chat and message, one answer stands) and records the fan-out behaviour for an operator decision.
- The Claude real-provider scenario overlaps S-CLT-03 in [claude-sdk-tools.md](../telegram-task-control/scenarios/claude-sdk-tools.md); one T3 run may satisfy both, reported under both IDs.
