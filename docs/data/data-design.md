# Data design

| | |
|---|---|
| Status | Baseline specification |
| Audience | Database administrator, developer, solution architect |
| Depends on | [Domain model](../domain/domain-model.md), [security and tenancy](../architecture/security-and-tenancy.md) |

Hydra has no database server. This document is the schema and the operating procedure for the SQLite files that are the product's memory.

## 1. Where state lives

Default root: `$XDG_STATE_HOME/hydra`, or `~/.local/state/hydra` when `XDG_STATE_HOME` is unset.

`HYDRA_DB`, when set, is the path of the original installation database. The identity registry and the account directory are derived beside that path, not from a second variable.

```text
$STATE/
├── hydra.sqlite                      original installation database (the owner's library)
├── hydra.sqlite.identities.sqlite    identity registry
└── hydra.sqlite.users/
    └── <account-id>/
        ├── hydra.sqlite              that account's library, runs, and execution state
        └── settings.json             that account's settings overrides

<checkout>/.hydra/settings.json       installation owner's overrides
```

`SETTINGS_FILE` overrides the owner's settings path only.

| Rule | Requirement |
|---|---|
| DM-01 | State lives outside the source checkout and outside every workspace directory. A database path inside a workspace is refused at startup. |
| DM-02 | Files are created mode `0600`. Directories that hold them are mode `0700`. WAL and shared-memory sidecars (the `-wal` and `-shm` files) get the same mode when they exist. |
| DM-03 | One live process family holds the instance lock for a state directory. A second writer is a misdeployment. |
| DM-04 | The owner's library is the original `hydra.sqlite`. Every other account uses the file under `hydra.sqlite.users/<id>/`. Registration never attaches a new account to the original file. |
| DM-05 | Settings are JSON files, not tables. Secrets in those files are plaintext. The database does not gain a copy of provider keys. |

## 2. Engine rules

Every database Hydra opens is SQLite with:

- `foreign_keys = ON` during application work,
- `journal_mode = WAL`,
- `busy_timeout = 5000`.

Foreign keys may be turned off only for the body of a migration that rebuilds a table, and they are turned back on before the migration version is recorded. A migration that needs that window says so. Application code does not turn them off.

Primary keys:

- Library entities (workspace, program, suite, work item, gates, drafts) use integer primary keys.
- Agent runs, pipeline runs, handoffs, audits, and delivery contracts use text ids generated by the server. Ids are not derived from provider session ids.

Timestamps that cross the wire are ISO-8601 text, except the identity registry and the execution tables, which use integer epoch milliseconds. A new table uses the convention of the database it lives in. It does not mix both in one table.

## 3. Identity registry

One file for the installation. Tables:

| Table | Key | Notes |
|---|---|---|
| `identity_user` | `id` text | `username` unique, case-insensitive. `password_hash` and `salt` only. `owns_legacy_data` is 0 or 1. |
| `identity_session` | `token_hash` | SHA-256 of the cookie token. `expires_at` integer. Cascade is by explicit delete, not by leaving stale tokens valid. |
| `identity_telegram_bot` | `id` checked equal to 1 | At most one bot. Token is stored here and nowhere else. |
| `identity_telegram_link` | `user_id` | `telegram_user_id` unique. `access` is `notify` or `control`. |
| `identity_telegram_code` | `code_hash` | Link codes. Expiry integer. |
| `identity_reset_code` | `user_id` | One outstanding recovery code. Hash, expiry, attempt count. |
| `identity_demo` | `user_id` | Expiry. Presence of the row is the demo flag. |
| `identity_telegram_audit` | integer | Append-only per user, capped at the most recent 200. |

**DM-06.** A partial unique index enforces at most one row with `owns_legacy_data = 1`.

**DM-07.** Deleting a user cascades to sessions, link, codes, demo, and audit inside this file. It does not, by foreign key, delete that user's account database. Account-file deletion is an application action (demo expiry, and any later account-deletion feature) that must name the directory explicitly.

The registry has no workspaces and no transcripts. A backup of an account database without this file loses the ownership flag and the ability to authenticate. A backup of this file without the account databases loses the work.

## 4. Account database catalogue

The catalogue is the schema the migrations are required to produce. It is grouped by aggregate. Columns listed are the ones behaviour depends on. A migration may add a column. It may not give a second meaning to a column named here.

### 4.1 Library

**`workspace`.** Id, unique case-insensitive name, unique `work_directory`, description, `claude_md`, `agents_md`, timestamps.

**`program`.** Belongs to a workspace, cascade delete. Unique `(workspace_id, name)` case-insensitive. Unique `(workspace_id, sort_order)`. Optional `external_key`, unique per workspace when not null.

**`suite`.** Belongs to a program, cascade delete. Unique name and sort order per program. Optional external key unique per program. Suite-level `default_provider` and `default_model` are the fallback assignment when a pipeline has no override row for that suite.

**`prompt`.** The work item. Belongs to a suite, cascade delete. Unique title and sort order per suite. Optional external key. Status text default `TODO`. `completed_at`, `result`, `is_gate`. Optional `parent_prompt_id` cascade, with `child_order`. Optional `station_policy_json`, validated as a station policy before write.

**`prompt_dependency`.** Pair of prompt ids, primary key both columns, check that they differ. Indexed on the target so "what depends on this" is a lookup.

**`program_gate`.** Belongs to a program. Unique prompt id (a work item is at most one gate). Unique `(program_id, code)` and sort order.

**`prompt_revision`.** Append-only snapshots of title and content with actor, reason, and time. Cascade with the prompt.

**`workspace_revision`.** Append-only snapshots of `claudeMd`, `agentsMd`, or `description`.

**`prompt_status_event`.** Append-only. Previous status, new status, reason, verification summary, actor, optional run id. The run id, when the schema declares a foreign key, sets null if the run row is rebuilt. The event survives.

**`prompt_remark`.** Append-only note. Kind, content, actor, optional run.

**`clarification_exchange`.** Question, answer, provider, model, state, times. Cascade with the prompt.

**`program_draft`.** Workspace, optional run id unique when set, state `PENDING`, `APPLIED`, or `DISCARDED`, goal, `body_json`, optional applied program id, optional target program and `baseline_json` for a revision of an existing program.

**`instruction_proposal`.** Workspace, field `claudeMd` or `agentsMd`, state as a draft, origin `request` or `run`, goal, baseline, content.

### 4.2 Pipeline definition

**`pipeline`.** Workspace, unique name per workspace, description, `auto_reassign` 0 or 1 default 0.

**`pipeline_stage`.** Primary key `(pipeline_id, suite_id)`, plus sort order.

**`pipeline_suite_agent`.** Primary key `(pipeline_id, suite_id)`. Default provider, model, and fallback list as JSON text. This row is the assignment for that pipeline. Absence of the row means "use the suite fallback".

**`pipeline_step`.** Primary key `(pipeline_id, prompt_id)`. Provider, model, `on_done` in `continue|stop|skip_rest`, `on_unfinished` in `continue|skip|wait`, fallback list, step order.

Scheduling reads `pipeline_suite_agent` for the pipeline first and the suite columns only as fallback. A write that names a pipeline upserts `pipeline_suite_agent` and does not change another pipeline's row.

### 4.3 Runs and threads

**`agent_run`.** Text id. Workspace cascade. Prompt id nullable and `ON DELETE CASCADE`; a custom chat run has a null prompt id, and deleting a work item deletes the runs that were for that item. Role check: `execute`, `consult`, `handoff`, `author`. Provider, model, state, start, end. `context_token_hash` and `token_expires_at` for the callback credential. Usage integers nullable. `stop_reason`, `session_id`, `thread_id`, `thread_title`, `display_text`, `wrapup_of`, `peak_memory_bytes`, `instruction_hash`, `permission_key`, `process_started`.

Partial unique index: one row per prompt id where state is `STARTING` or `RUNNING` and role is `execute`.

Indexes: by prompt and start; by workspace, role, and start; by thread and start.

**`agent_run_event`.** Integer id, run id cascade, `event_json`, created at. This is the transcript. Retention deletes from this table.

**`agent_command`.** Primary key `(run_id, request_id)`. Operation name and response. Idempotency for callbacks. Optional request hash so a replay returns the stored response.

**`run_message`.** Asides. Direction `OPERATOR` or `AGENT`. Delivery `native`, `inbox`, or `resume`. State `QUEUED`, `DELIVERED`, or `SUPERSEDED`.

**`chat_thread`.** Primary key `(workspace_id, thread_id)`. Title, pinned, archived, updated time, last reply, last read. Triggers on `agent_run` insert and on thread association keep a thread row from going missing when a run is recorded. Application code still owns pin, archive, and title edits. A hand-inserted `agent_run` in a maintenance script will fire those triggers.

**`run_change_set`.** Primary key `run_id`. Repository root, branch, base commit, head commit, state `PENDING|UNCHANGED|COMMITTED|NEEDS_COMMIT|UNAVAILABLE`, file and line counts, commit count, message, times.

### 4.4 Pipeline runs

**`pipeline_run`.** Text id. Pipeline cascade, workspace, state check as in the domain lifecycle, current suite, current suite-run id, play provider and model, times, `stop_reason`, `wait_reason`. Partial unique index: one row per pipeline in `PLAYING`, `WAITING_HUMAN`, or `PAUSED`.

**`suite_pipeline_run`.** The stage run. State check as above. Current prompt, current agent run, attempt, pipeline run id, wait reason. Partial unique index: one row per suite in `PLAYING`, `WAITING_HUMAN`, or `PAUSED`.

**`handoff`.** Text id. Source run unique. Successor run. State `QUEUED|RUNNING|READY|FAILED|SUPERSEDED`. Partial unique index for one active handoff per prompt.

### 4.5 Done, verification, audit

**`definition_of_done`.** Unique `(scope, scope_id)` with scope `workspace|program|suite|prompt`. Enforcement `block|warn|off`.

**`dod_criterion`.** Belongs to a definition, cascade. Kind `PROSE|COMMAND|CHILDREN_CLOSED`. Command, cwd, expected exit code, timeout, required flag, order. `supervisor_only` integer default 0.

**`dod_result`.** Prompt cascade, criterion cascade. Source and result checks as in the domain model. Output, exit code, evidence text. Hashes the supervisor uses to know whether inputs changed: `input_hash`, `recipe_hash`, `environment_hash`, `stable_inputs`.

**DM-08.** `dod_result.run_id` is a label, not a foreign key. Evidence must survive a rebuild of `agent_run`. Adding a cascading foreign key here is a schema defect, not a tidy-up. A stale run id means "that run row is gone", and the evidence remains.

**`suite_verification`.** Suite cascade, workspace, kind, optional run id unique when set, provider, model, state, verdict, `summary_json`, report markdown, `stats_json`, times, optional scope prompt.

**`suite_verification_item`** and **`suite_verification_event`.** Cascade with the verification.

**`completion_audit`.** Text id. Source run, optional audit run, verdict `COMPLETE|INCOMPLETE|UNVERIFIABLE`, report JSON and markdown, `applied`, error, times. Partial unique index for one active audit per prompt.

**`status_definition`** and **`trigger_definition`.** The account's catalogue and trigger sentences. Seeded from the defaults in the domain model. Locked flags are enforced in the application, not only by a check constraint, because the lock set differs per status.

### 4.6 Supervised execution

These tables share the account database. They are one aggregate with the delivery contract.

| Table | Role |
|---|---|
| `delivery_contract` | One per prompt id. Engine `shadow` or `supervised`. Desired `RUNNING`, `PAUSED`, or `STOPPED`. Phase, revision, generation, version. JSON for authority, criteria, and policy, each validated before write. |
| `delivery_contract_version` | Primary key `(contract_id, version)`. The allocation history, including the reason. |
| `execution_plan` | Primary key `(contract_id, revision)`. `plan_json` is a validated plan. |
| `work_unit_meta` | Primary key prompt id. Accepted time, recovery stage, unit JSON. |
| `shared_verification` | Primary key `(contract_id, prompt_id)`. |
| `execution_event` | Append-only. Unique `event_id`, payload JSON and payload hash. Not subject to transcript retention. |
| `dispatch_outbox` | Unique `request_key`, unique `run_id`. State `PENDING|CLAIMED|RUNNING|SETTLED|QUARANTINED|CANCELLED`. |
| `execution_lease` | Primary key resource. Fencing token and expiry. |
| `budget_ledger` | Primary key effect id, referencing the outbox. Reserved and actual time and tokens. `unknown_usage`. |
| `recovery_case` | Primary key `(contract_id, prompt_id, signature, remedy)`. |
| `execution_wakeup` | One wake-up per contract. |
| `command_task` | A server-side command criterion execution, with recipe, input, and environment hashes, deadline, and a link to the `dod_result` it produced. |

JSON in this aggregate is the validated document. Anything the scheduler polls (state, due time, generation, revision, desired state, phase) is a real column.

## 5. JSON, and when not to use it

A column may be JSON when all of these hold:

1. The document is validated by a shared model before insert.
2. The scheduler does not filter or join on fields inside it.
3. Readers of the row want the whole document.

Draft bodies, station policies, execution plans, verification summaries, and transcript events meet that test. Status, provider id, pipeline state, and budget reservations do not. A new feature that wants to query "all stations whose verifier is X" promotes the verifier to a column in a new migration rather than scanning `station_policy_json`.

## 6. Migrations

**DM-09.** The account database records applied versions in `schema_migration(version, applied_at)`. Opening the database runs every version greater than the maximum recorded, inside a transaction, in order, then records the version.

**DM-10.** A version that has been published is immutable. Operators will have it applied. The next change is the next integer.

**DM-11.** Migrations are additive: new tables, new columns with defaults, new indexes, or a copy-forward into a new table followed by a rename. They do not drop a column the running code still reads. They do not rewrite an operator's work-item text except where a specified seed creates the initial revision row.

**DM-12.** Migrations run on the operator's database the next time the console opens it. They are tried on a copy first. The sandbox exists for that try. They are not tried by pointing a development process at the live file.

**DM-13.** The identity registry is created idempotently with `CREATE TABLE IF NOT EXISTS` because it has no second writer and a short table list. The account database is not managed that way. Account schema changes go through `schema_migration`.

## 7. Retention

A scheduled job, and a pass after boot, deletes `agent_run_event` rows so that each run keeps at most the configured event count (default 4,000) and drops events older than the configured age (default 30 days), while always keeping the newest configured tail (default 200).

The job shall not delete:

- `agent_run`
- `prompt_status_event`, `prompt_remark`, `agent_command`
- `run_change_set`
- `execution_event`, `budget_ledger`, `delivery_contract_version`
- identity audit rows, which have their own cap

Deleting events does not return disk to the operating system. Shrinking the file is an offline `VACUUM`, specified below.

## 8. Backup and restore

The backup set is:

1. The identity registry, including its `-wal` and `-shm` if the copy is raw and the process is stopped.
2. The original installation database.
3. Every directory under `hydra.sqlite.users/`.
4. The owner's settings file and every account `settings.json`.

Preferred method: SQLite's online backup API, one file at a time, then a copy of the settings files. Acceptable method: stop the console, copy the files, start the console.

A raw copy of a WAL database while the console is running is not a backup. It can tear.

Restore replaces the whole set. Restoring account databases without the registry loses ownership and logins. Restoring the registry without the account databases yields accounts that authenticate into empty or missing files. The product is not required to reconstruct one side from the other.

After a restore onto a new path, `HYDRA_DB` points at the restored installation database. The registry and user directories must sit beside it under the same names the derivation rule uses.

**Password reset is not a restore.** The reset command updates `identity_user` in place.

**VACUUM.** Stop the console. Run `VACUUM` on the file that grew. Start the console. Do not VACUUM the live file out from under a running writer.

## 9. Investigation

To look at a live problem:

- Copy the files, or open SQLite with `mode=ro` and `immutable=1` when a copy is impractical.
- Do not run migrations against the live file from a second checkout.
- Do not `UPDATE` status columns by hand. A status change that bypasses `prompt_status_event` breaks INV-04.
- Do not delete `identity_user` rows to "fix" a password.
- Do not add the foreign key that DM-08 forbids.

A read-only session is still a reader on a WAL database. Keep it short, and do not leave a GUI tool holding the file while a pipeline runs if that tool takes a write lock by default.

## 10. Integrity checklist

A database that satisfies this design can say yes to all of the following.

- `PRAGMA foreign_keys` is on for application connections.
- `PRAGMA journal_mode` is `wal`.
- There is at most one identity user with `owns_legacy_data = 1`.
- There is no active `execute` pair on the same prompt id.
- There is no pair of non-terminal pipeline runs for the same pipeline.
- Every `pipeline_stage.suite_id` references a suite. Every `pipeline_step.prompt_id` references a prompt.
- Every `prompt_dependency` row has two different ids, and the graph built from the table has no cycle. The cycle check is application-level; SQLite will not do it.
- Every non-null `dod_result.source` and `result` sits inside the checks.
- `schema_migration.version` values are contiguous from 1 to the maximum. A gap means a migration was skipped, which is a defect.
- Settings files are not inside the database, and provider key material does not appear in any text column of either database. Run credentials appear only as hashes.

## 11. What a future table has to decide

Before adding a table, the change names:

1. Which aggregate owns it, and the cascade when the owner disappears.
2. Which uniqueness rule is a partial index because it applies only to "active" rows.
3. Whether each new column is a query predicate or a document.
4. The migration version, written as a new block, tried on a copy.
5. Which retention rule applies, defaulting to "keep the row".
