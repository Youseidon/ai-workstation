# Hydra — agent working agreement

This file is the single set of instructions for every coding agent working in
this repository (Claude Code reads it through `CLAUDE.md`). There are no nested
instruction files: keep it that way and add to this one.

## What this is

Hydra is a self-hosted web console that drives six local CLI coding agents —
Claude Code, Codex CLI, Cursor CLI, Grok CLI, GitHub Copilot and Kilo Code —
from one browser UI, and chains them into autonomous pipelines of workspaces,
programs, suites and prompts. `README.md` is the user-facing reference; read
the relevant section before changing a behaviour it documents.

It is a local tool with account login and separate account runtimes. It runs arbitrary code in configured
workspaces through every provider, so treat permission, sandbox and
environment-scrubbing code as security-sensitive.

## Repository layout

npm workspaces, TypeScript throughout, Node ≥ 20.10.

| Path | Role |
|---|---|
| `shared/` | `@hydra/shared`: `contracts/` owns wire/record shapes, `models/` owns catalogs and domain values, `policies/` owns decisions, `utils/` owns shared helpers; `src/index.ts` explicitly exports the public API. Consumed as raw TypeScript by both other packages. |
| `server/src/` | Backend: stable `index.ts` entrypoint, `api/` transport, `services/` orchestration, `repositories/` SQLite stores and migrations, `domain/` pure rules, `config/` settings, `infrastructure/` OS integration, `contracts/` service interfaces, `models/` state/context models, `utils/` general helpers. |
| `server/src/providers/` | `adapters/` normalizes each provider into shared events; `streams/` handles native streams; `registry.ts` is the provider table. Usage, discovery, auth and updates live alongside them. |
| `server/bin/` | Executables handed to agents at run time (`agent-step.mjs`, `cursor-policy.mjs`). |
| `server/test/`, `shared/test/`, `web/test/` | `node:test` suites, one `*.test.ts` per module or behaviour. |
| `web/` | Next.js App Router frontend: `app/` routes; `features/<feature>/{components,hooks,lib}/` feature code; `components/{ui,layout,theme}/` shared UI; `contexts/` app state (`hydra.tsx` owns the WebSocket); `models/` browser state shapes; `hooks/` app hooks; `api/` HTTP client; `lib/` shared browser utilities. |
| `brand/` | Logo, icons and brand guidelines (`README.md`, `guidelines.html`). Every asset — including `web/app/{favicon.ico,icon.svg,apple-icon.png}`, `web/public/brand/` and `web/components/brand/geometry.ts` — is generated by `node brand/build.mjs`; change the generator, never an output. |
| `scripts/` | `free-ports.mjs` (run by `npm run serve`) and `dev-sandbox.mjs` (`npm run dev:sandbox`). |

## Commands

```bash
npm install
npm run typecheck                 # shared, server, web
npm test --workspace shared       # run each workspace separately: the root
npm test --workspace server       # `npm test` chains with &&, so one failing
npm test --workspace web          # server test hides every web result
npm run lint --workspace web
npm run dev:sandbox               # develop against a copy of the live database (:4100 / :3100)
```

Run typecheck and the tests of every workspace you touched before calling work
done. A change to `shared/` touches all three. Report failures as they are;
compare against a baseline run rather than assuming a failure is yours or not.

## Live-system safety — read before running anything

The operator runs live pipelines from this checkout with `npm run serve`
(server :4000, web :3000). Agents may be mid-task in other repositories.

- **Never run `npm run serve`, `npm run free-ports` or `npm run dev` unless the
  operator asks.** `serve` and `free-ports` kill whatever holds ports 3000 and
  4000 — that is the live console. `dev` runs under `tsx watch`, which restarts
  on every save and kills every agent in flight; it refuses the live database
  by default for that reason. Use `npm run dev:sandbox`.
- **Never open, write or delete the live database**
  (`~/.local/state/hydra/hydra.sqlite`, or `$HYDRA_DB`). Tests and scripts use
  a disposable file through `HYDRA_DB`; the server test script already does.
  For investigation, copy it, or open it with `{ readonly: true }`.
- **Schema migrations** are the versioned blocks in the `migrate` transaction
  in `server/src/repositories/workspaces.ts`. They run on import, against the live database,
  on the next `serve`. Add a new version; never edit an applied one. Keep them
  additive and try them in `dev:sandbox` first.
- **Child-process environment scrubbing.** Agents and verification commands
  must never learn where Hydra's own state is. The `HYDRA_DB`,
  `HYDRA_DATA_DIR` and `HYDRA_DATABASE_PATH` variables are removed from child
  environments in `providers/adapters/claude.ts`, `providers/adapters/codex.ts`,
  `providers/adapters/spawnAdapter.ts`, `infrastructure/resourceContainment.ts` and
  `services/verification/dodCommands.ts`. A new variable that points at state belongs in all five.
  Account gateway credentials (`HYDRA_WORKER_SECRET`) must also be scrubbed in
  all five; private runtimes must reject application traffic without them.
- Secrets live in `.env` and `.hydra/settings.json` (both gitignored). Never
  print them, commit them or send them to the browser — the client only ever
  sees whether a key is set.

## Architecture rules

- **Providers stay behind their adapter.** Every adapter implements
  `AgentAdapter` (`contracts/agentAdapter.ts`) and yields only the normalized event
  types from `shared/` (`assistant_text`, `tool_use`, `tool_result`, `status`,
  `result`, `error`). Provider-specific shapes never leave the adapter. A new
  provider is one adapter file, one `registry.ts` entry, its id in
  `PROVIDER_IDS` and a chip colour — nothing else.
- **The server owns run truth**: run id, elapsed clock (status heartbeat),
  token usage and terminal state. The browser renders; it never derives these.
- **Stream, don't buffer.** Events go to the socket as the adapter yields them.
- **Failures are events.** A crashed child, malformed stream or provider error
  becomes an `error` event, never a dropped socket. Child `stderr` goes to the
  server log, not the browser, except as the tail of a fatal error.
- **Settings are table-driven.** The Agents page renders from the server's
  field table in `config/settings.ts`; add a setting there, not in the UI.
- **The browser talks to the server only.** No direct SQLite or filesystem
  access from `web/`.
- **Git belongs to the operator.** The app never stashes, resets or commits
  the operator's own changes; agent work is committed through
  `agent-step checkpoint`. Preserve that in any code touching `gitChanges.ts`
  or workspace runs.

## Code conventions

- Follow the placement guide in README's Architecture section. Feature/domain
  ownership comes before generic helpers. Keep internal shared imports direct;
  use explicit named re-exports only at the public `@hydra/shared` boundary.
- Tests mirror their source responsibility under each workspace's `test/`;
  cross-module backend flows go in `server/test/integration/`.

- TypeScript `strict` with `noUncheckedIndexedAccess` and
  `verbatimModuleSyntax`: use `import type` for type-only imports and handle
  the `undefined` from indexed access rather than asserting it away.
- ESM everywhere. Server and shared sources import local files with explicit
  `.ts` extensions (`./utils/logger.ts`); web uses the `@/` alias.
- Shared types and validators go in `shared/src/` and are imported from
  `@hydra/shared` — do not redefine protocol types locally.
- Comments explain *why*: the constraint, the incident or the failure mode a
  piece of code exists to prevent. Match that style; skip comments that only
  restate the code.
- Tests use `node:test` + `node:assert/strict`, run through `tsx`. Server
  tests run serially against a temporary database; never point one at real
  state. Add or update tests alongside behaviour changes.
- Environment variables are prefixed `HYDRA_`; browser storage keys `hydra.`.

## Next.js

`web/` runs Next.js 16, whose APIs and conventions differ from older versions
and likely from your training data. Before writing Next.js code, read the
relevant guide in `node_modules/next/dist/docs/` (installed at the repository
root) and heed deprecation notices. `agentRules: false` in `web/next.config.ts`
stops `next dev` from regenerating its own `web/AGENTS.md`.

## Instruction files and workspaces

Hydra writes a workspace's stored `CLAUDE.md` and `AGENTS.md` into that
workspace's root before every run (`server/src/services/workspaces/workspaceInstructions.ts`). If a
Hydra workspace is ever pointed at this repository, its stored text will
overwrite these files and edits to them become proposals. Keep such a
workspace's instruction fields empty, or make them identical to these files.

## Git

- The working tree often holds the operator's uncommitted work. Do not stash,
  reset, checkout or clean it; commit only when asked, and only your changes.
- Commit subjects are short, lowercase, imperative summaries
  (`fix cursor issue`, `pipeline page UX improved`).
